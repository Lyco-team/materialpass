一、自我介绍
———————————————————————————————

云枢智创数码信息科技服务工作室 · lilyco-42。我们平时用 lilyco（自研 Rust 工具框架）做自己的生产力工具，

———————————————————————————————
二、你的作品是什么
———————————————————————————————

一句话：去窗口办业务的普通人（尤其是不会折腾手机的长辈），把身份证、证件照、证明、合同这类材料
集中保管起来、一键处理成系统要求的规格、让 AI 先预审一遍，最后由人类签字提交。

线上地址：https://materialpass-r96hu96ehfl.qoder.zone （Qoder Sites 部署，公开访问，无需登录、无需装任何东西）
源码：<https://github.com/lilyco-42/materialpass>

———————————————————————————————
三、为什么做
———————————————————————————————

有一次我们在市场监督管理局的窗口，看到一位老人抱着一摞材料慢慢填表：

· 同一组信息（姓名、身份证号、手机号）要在每张表上重抄一遍；
· 照片因为「文件超过 100KB」被系统退回，他当场用手机压缩，压完看不清，又退回；
· 扫描件缺了身份证背面，只能回家拿、再跑一趟。

真正消耗人的不是「填」这个动作，而是三件事：材料到处散、规格看不懂、错了要重跑。

所以我们做了一个刻意克制的产品判断：不做「AI 帮你自动提交」。政务场景里，AI 自动提交是危险且
不可追责的。材料通做的是——

· AI 负责预审：把「这张照片像素不对」「这个证件还有 20 天过期」「这三个字段是空的」
  在人按下提交键之前说清楚；
· 人类负责签字：代码层面写死了 approve 动作必须显式带 byHuman: true，否则直接抛错。
  AI 不能自己批自己准备的材料。任何字段改动都会把草稿打回「待复核」。

另外它解决了 Agent 做政务填报时的真问题：绝大多数网页对 Agent 只有像素没有语义，Agent 只能截图
猜坐标，猜错就提交错材料。材料通的每个可交互元素都带语义路径，人类点按钮和 Agent 调 invoke()
走同一套 action、同一条校验链——没有截图猜坐标，也没有 AI 专用旁路。

四、怎么用（5 步，你照着就能跑通）
———————————————————————————————

打开 https://materialpass-r96hu96ehfl.qoder.zone 后直接进「上手」页，每一步右边都有「带我去做」按钮。

1. 建档案 — 资料库页填姓名、证件号、联系方式。一次填完，以后所有表都从这里取。空库时可以点「载入示例档案」。
2. 放材料 — 拖一张证件照或扫描件进来，给它选目标规格（一寸照 / 身份证 / 营业执照…），登记有效期。
3. 对齐规格 — 点「一键对齐」：比例不对会居中裁切，尺寸不对会缩放，体积超标先降质量、质量见底再降分辨率。
   每一步操作痕迹都留在日志里，可回看。（处理前 / 处理后并排显示）
4. 跑预审 — 先看本地确定性规则（格式 / 体积 / 像素 / 有效期 / 空字段），再可选开启 AI 做语义审查
   （姓名是否各处一致、材料是否互相矛盾、是否缺关键页）。问题清单每条都能点回对应材料。
5. 人工签字 — 生成草稿，逐字段核对，点「批准」并写复核意见（会弹二次确认，明确提示「你正在以人类身份签字」）。
   只有 approved 的草稿才能导出提交包。

隐私：全程纯前端，没有任何上传。文件只进本机 IndexedDB，图片在浏览器 Canvas 里处理，备份导出必须
PBKDF2 + AES-GCM 加密，密码不离开本机。零遥测、零第三方请求。AI 预审默认关闭；开启时只把字段文本
和材料元数据发给你自己填的 API，绝不发图片二进制。

五、用 Qoder 做出来的过程
———————————————————————————————

1）预研与选型（省掉最多时间的一步）
我们只给了一句需求，Qoder 先做了调查而不是直接写代码：
· 扫了本机 30+ 个仓库和 GitHub 现状，指出大赛硬性要求其实不是 GitHub，而是 Qoder Sites 公开链接 +
  天池作品帖（规则里明确「原则上不接受本地文件、压缩包」），并发现本地根本没有 .qoder.site 描述符
  ——真正的缺口在部署这一步；
· 更关键的是它发现这个想法我们自己已经实现过一半：lilyco-web2cli 里已经有政务填表闭环（资料库分类、
  Cookie 导入、AI 预填草稿、人类审核闸门、受控提交、CDP 附着已登录浏览器）。于是方案从「重写一个引擎」
  改成「做它的 Web 前端 + 客户端材料处理」：资料库导出与 Rust 侧 VaultProfile 逐字段一致（这一步后来
  用真实 CLI 跑通验证过），草稿侧对齐字段命名与 status 取值，跨站点真正发包那条链由 CLI 的
  prepare-submit 生成带 command 的草稿。这一步至少省掉一周的重复劳动。

2）技术栈对齐
Qoder 读取 lilyco 官方 lilyco-template/web 底座（React 19 + Vite 6 + Tailwind v4 + shadcn oklch 令牌），
直接复用，没有手搓 CSS 导致风格飘移。依赖安装 911ms 完成。

3）代码实现
src/lib/ 数据层（类型 / 规格库与规则引擎 / Canvas 图像处理 / WebCrypto 加密保管箱 / 单一状态源 store /
AI 原生协议桥 / 可选 AI 预审）由 Qoder 编写；六个页面与 UI 原语由 Qoder 子任务并行完成。
TypeScript 严格模式零错误，pnpm build 一次通过（413 KB / gzip 127 KB）。

4）端到端验证（都是真跑出来的结果，不是「应该可以」）
Qoder 用本机 ego-lite 浏览器（人机共用浏览器，Agent 操作时界面会显示协作指示器）把五步流程跑了一遍，
并逐条验证产品主张：

· Agent 写档案字段后，人类 DOM 立刻看到同一个值 → 10 个字段写入，DOM 读回一致
· 一键对齐规格（600×900 PNG → 一寸照）→ 居中裁切 → 缩放 295×413 JPEG，70KB → 9KB，日志留痕
· 实时预览是否等于一键对齐的结果 → 两者共用 specTransform()，尺寸/体积/格式一致
· AI 试图自己批准自己的草稿 → 被闸门拦住，抛「批准必须由人类操作」
· 未批准草稿能否导出 → 被拒绝
· 人类在二次确认弹窗里勾选并签字（真实点击按钮，不是调 API）→ 草稿转 approved，导出 1251 字节提交包
· 签字后再改一个字段 → 草稿自动回到 pending_review，闸门重新生效
· 语义路径是否有一对多歧义 → ambiguous() 返回 {}，30 条路径全部唯一命中
· 390px 手机视口下六个页面是否横向溢出 → 每页 scrollWidth 都等于 390，表格/代码块在自己盒子里滚动
· 触屏下的点击目标尺寸 → (pointer: coarse) 时按钮与输入控件 ≥44px，鼠标设备仍是紧凑尺寸
· 生产构建启动是否有控制台/网络报错 → 零报错零警告，零第三方请求
· 网页导出的资料库能否被真实 lweb2cli 二进制导入 → vault --op import 返回 imported:true，5 个分类、2 份附件全部落库
· 线上站点（Qoder Sites 公开域名）匿名访问 → 首页与 /manifest.json 都是 200；浏览器里桥挂载、14 个动作、
  ambiguous() 仍是 {}、无横向溢出
· 线上部署版跑完整五步（不是本地构建）→ 真实文件控件上传 → 刷新页面材料仍在（IndexedDB 在该 origin 生效）
  → 一键对齐 295×413 / 9KB → 预审 0 错 0 警 → AI 自批被拒 → 未签字导出被拒 → 人类签字后导出 1106 字节 /
  2 份附件 → 改一个字段回到 pending_review；控制台零报错
· 线上导出的资料库再次喂给真实 CLI → 同样 imported:true（5 分类 / 2 附件）。踩到的坑：Agent 拿到的返回是
  {ok, json} 信封，落盘必须写 .json 字段本身，整个信封存文件会让 CLI 报 missing field name

5）发现并修掉五个真实缺陷（都是边跑边查出来的，不是我们提的）
· app.tab.vault 匹配到 2 个元素：响应式布局里侧边导航和窄屏导航共用了同一路径，Agent 定位会失败。
  Qoder 把窄屏导航改成独立命名空间 app.tabbar.*，并且加了一个自检动作 ambiguous()，
  让页面自己报告歧义地址——现在返回 {}。
· 缩放日志把「从 → 到」打成了同样的数值（因为先赋值再拼字符串），已修。
· 预览与结果不一致：材料处理页右侧写着「处理后（实时预览）」，但它没带上目标规格的像素尺寸，
  于是 600×900 的原图旁边显示的还是 600×900，而「一键对齐」实际会产出 295×413。
  抽出 specTransform() 让 store 和页面共用同一份几何计算后，预览即结果。
· 窄屏把整页撑到 1020px：用 390px 手机视口跑六个页面，Agent 页的文档宽度是 1020px——
  长 JSON 示例和语义路径列表作为网格子项按 min-width:auto 取了自己的最小内容宽度，整页被迫横向滚动。
  给卡片与示例块加 min-w-0、让代码块在自己的盒子里滚动后，六个页面 scrollWidth 全部回到 390；
  同时补了一条 @media (pointer: coarse) 规则，触屏下点击目标 ≥44px。这条是受众决定的：
  长辈多半是用手机单手点的。
· 文档里的互通命令是错的：README 和 manifest.json 都写着 lweb2cli vault import --json …，看着很像回事；
  真把网页导出的 JSON 交给二进制时才发现这个子命令不存在——--json 只是输出格式开关，导入是
  vault --op import --profile <名> --file <json>。顺手核对 Rust 源码又发现 SubmissionDraft 有个必填的
  command（WebCommandSpec），所以「草稿也逐字段对齐」属于过度宣称。两处都按 --help 和源码改过，
  导入也真跑通了。互通这件事，跑一遍才算数。

6）部署到 Qoder Sites（大赛硬性要求的那一步）
没有自己搭服务器、没有写部署脚本：Qoder 用 Sites 的宿主命令把 dist 打包成不可变草稿（prepare_site），
读回 artifactReady / canPublish / blockers 确认没有阻塞后 publish_site，再把访问策略从 private 改成
public（这一步要显式确认公开）。最终公开地址 https://materialpass-r96hu96ehfl.qoder.zone，
GitHub 仓库的 homepage 也指到这里。

7）我们人工改 / 决定的部分
· 产品主张本身：「不做自动提交、AI 只能预审、人类必须签字」这条来自我们在窗口边的观察，
  写进了 approve 的 byHuman: true 硬约束和 README 的取舍说明。
· 规格数值不做权威宣称：各地政务系统要求差异极大，我们把每一项做成可编辑预设，
  校验时只说「与你设定的规格不符」，不假装这是官方标准。这条是我们要求改的。
· 赛道选择：报 Hack4Good（技术向善 / 老年人数字鸿沟）。
· 无障碍取向：受众是长辈和办事窗口，要求按钮和文字加大、对比度提高、少用嵌套交互，
  重要状态用文字说明而不只是颜色；纯键盘能走完五步。
· 命名与文案：品牌、页面标题、五步引导的中文表述全部人工定稿。

附：技术要点
———————————————————————————————

· 单一状态源：所有状态在 src/lib/store.ts，UI 通过 useSyncExternalStore 订阅，不留平行状态。
· lilyco-native-web/1 协议：window.__materialpass.invoke(action, params)，14 个动作，
  机器可读契约在 /manifest.json。
· 与 lilyco-web2cli 互通：lweb2cli vault --op import --profile <名> --file <json> → prepare-submit → review --op approve →
  commit-submit。网页负责人类看得懂改得动，CLI 负责跨站点真填报。
· 许可 MIT，属于 lilyco 生态：<https://github.com/lilyco-42/lilyco>
